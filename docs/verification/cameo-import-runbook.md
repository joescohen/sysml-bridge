## (b) What this artifact exercises, and what's out of scope for this pass

`examples/weave-mini/build-weave-model.ts` runs the REAL weaver pipeline (mentions → autoCluster
→ enumerateChains/applyChainTypeGate) over the weave-mini 3-document prose corpus
(`examples/weave-mini/corpus/`), against a recorded fixture LLM provider (zero API key,
byte-identical every run — see the script's own header comment). The resulting model:

- **33 elements**: 10 requirement usages (`REQ-001`..`REQ-010`) + 1 need usage (`N-001`) in a
  `Cargo Handling Requirements` package; 9 component part usages (8 top-level + `Position Sensor
  Array` nested inside `Cargo Handling Controller`) in a `Cargo Handling Subsystem` container; 6
  function action usages in a `Cargo Handling Operations` container; 2 mode state usages in a
  `Cargo Handling Modes` state def; 1 verification case.
- **satisfy**: `satisfy 'REQ-001' by 'Detect Cargo Presence';`
- **derive**: `dependency from 'REQ-001' to 'N-001';`
- **verify**: `verification def Verify_REQ_001 { objective { verify 'REQ-001'; } }`
- **containment-fed allocation chain** (`allocation ∘ containment → allocation`, the W2 chain
  composer): `Detect Cargo Presence` is allocated to `Position Sensor Array` (accepted relation
  r1), `Position Sensor Array` is structurally nested inside `Cargo Handling Controller`
  (accepted relation r2, containment), and the chain composer derives a THIRD, composed allocation
  `Detect Cargo Presence` → `Cargo Handling Controller` — all three are visible in the file (r1 and
  the composed result as flat `allocate` statements; r2 as the nesting itself).
- **`CHC`** is deliberately kept as a SEPARATE, unmerged component (the acronym-alias entity the
  band-2 `suggestMerges` proposer flags for human review) — a live, honest demonstration of
  no-auto-approve: the model shows the pre-merge state, not a silently-applied guess.

**`corpus = null` for the Gate 1 `audit()` call** (visible in the script and in the
`GATE03-corpus-unavailable` warning above): weave-mini has no ANGARS-style hand-extracted
`extracted.json`; it's a prose corpus ingested through the LLM candidate pipeline, not a
structured extraction. Passing `null` degrades ONLY the corpus-gated provenance-existence /
fidelity checks to that one warning — `relationalFindings` (including R4-def-operand),
`coverageMatrix`, and the full `ENT-*` entity rule pack (run with the REAL `entities` +
`mentionIds` from this corpus) all still run at full strength. This is an honest scope choice,
not a gap papered over.

**Out of scope for this artifact** (by deliberate choice, to keep risk low since nobody could
verify against live Cameo in this session): the 63 cross-document co-occurrence candidates and
the 1 suggested acronym merge (`enumerateCooccurrence` / `suggestMerges` — both W1/W2 machinery)
are computed and logged by the generator (proving the enumerators run over this corpus) but are
NOT written into the model — they are PROPOSALS, and per no-auto-approve a proposal is not a fact
until a human approves it in the review queue.

## (c) Known semantic risks the local grammar validator can't catch

The local validator (`tools/sysml-validator`) is ANTLR-grammar-only — it proves the file *parses*,
never that Cameo's semantic resolver *accepts* it. Per `CLAUDE.md` R2/R4 and
`docs/verification/gate3-cameo-import.md` (b), here is what's covered where:

| Risk class | Locally gated? | How |
|---|---|---|
| Definition operand on `satisfy`/`allocate`/`verify` (Cameo: "X cannot be cast to Feature") | **Yes** — `R4-def-operand` in `packages/gates/src/relational.ts`, run in Gate 1 above (0 errors, and independently proven to fire — see the positive control in this session's report) | Every element this artifact's trace relationships reference is typed `RequirementUsage`/`PartUsage`/`ActionUsage` — never a `*Definition`. Zero `def` keyword occurrences reference a trace operand in the file (spot-check: `grep -n '\bdef\b' examples/weave-mini/weave-model.sysml` shows only `verification def Verify_REQ_001`, which OWNS the `verify` statement, is not its operand). |
| Dangling / unresolved reference (a `satisfy`/`allocate` endpoint that doesn't resolve to any declared element) | **Yes** — `GATE02-dangling-endpoint` in the same rule pack | 0 findings (Gate 1 above). |
| Duplicate element/relationship id | **Yes** — `GATE02-id-duplicate` | 0 findings. |
| Entity resolution invariants (unapproved merge, dangling mention reference, duplicate-suspect) | **Yes** — `ENT-*` rule pack (`packages/gates/src/entities.ts`), run with this artifact's REAL `entities`/`mentionIds` | 0 findings — the `CHC` / `Cargo Handling Controller` acronym pair and the `Interlock` mode-vs-component trap both correctly produced zero `ENT-duplicate-suspect`/`ENT-unapproved-merge` findings. |
| **Name resolution ambiguity** — two elements with the same literal name in overlapping scopes | **NOT locally gated** — the grammar validator doesn't do semantic name resolution, and `packages/gates` has no rule for this class today | This artifact avoids the one known collision by construction (`Interlock` the component vs. `Interlock` the mode — the corpus TRAP — is disambiguated to `Interlock Mode` in the mode's presentation name; see the code comment in `build-weave-model.ts`). No other name collisions exist in this artifact (verified by inspection: every element name is used exactly once as a declaration). |
| **Multiplicities** — this artifact declares none (no `[mult]` on any usage) | **N/A this artifact** | Nothing to check; flagged here only because it's a known gap class for a *future* artifact that does use multiplicities. |
| Cameo-version-specific behavior (deprecated syntax, editor quirks, license-tier feature gates) | **Not gatable locally at all** | Only a live Cameo session can surface these — this is exactly what section (e) below exists to capture. |

## (f) Report-back loop — turning a live Cameo error into a permanent local gate

This is the compound-engineering loop the brief asks for: the FIRST live Cameo import is expected
to surface something the local gates don't yet check (that's the whole reason Gate 3 exists — the
local validator is grammar-only, `packages/gates` checks the semantic classes already known about,
and Cameo is still the only oracle for everything else). When Cameo reports a diagnostic this
runbook's checklist didn't predict:

1. **Capture it verbatim** in EVIDENCE below — the exact diagnostic text, which element/line it
   points at, and whether it blocked synchronize or was advisory.
2. **Classify it**:
   - **Grammar-shaped** (the local validator should have caught this but didn't): read
     `docs/sysml-v2-reference/` (the vendored `.g4` grammar + `cheatsheet.md`) to understand the
     correct form — never guess syntax from memory (R1). This likely means the vendored grammar
     or `tools/sysml-validator/validate_sysml.py` has a gap; file it as a grammar-reference fix.
   - **Semantic, and general** (would recur for any model shaping data this way, not specific to
     weave-mini's corpus): this is the case that becomes a NEW rule in `packages/gates/src/`,
     mirroring how `R4-def-operand` was added after exactly this kind of discovery (see
     `docs/verification/gate3-cameo-import.md`'s own history). Per the project's gate discipline,
     a new rule ships WITH a planted, positive-control seeded defect (see
     `examples/angars/pipeline/seeded-defects.ts` for the existing pattern) — a rule that has never
     been shown to fire is not yet a trustworthy rule.
   - **Semantic, but narrow/version-specific** (a quirk of this Cameo build/license tier, not a
     general SysML v2 semantic rule): document it in this runbook's EVIDENCE and in the "Known
     semantic risks" table in section (c) — it doesn't need a code change, but it does need a
     durable written record so the next importer isn't surprised.
3. **Fix the SOURCE, never the artifact.** Per R2/gate3's precedent: fix
   `examples/weave-mini/build-weave-model.ts` (or the shared `packages/sysml/src/sysml-serializer.ts`
   / `packages/gates/src/*` it depends on), never hand-patch the committed `.sysml` text — a
   hand-patch would immediately go stale on the next regeneration and the assertion script would
   (correctly) fail the byte-identity check.
4. **Re-run the full local gate** (this doc's section (a), plus
   `pnpm tsx examples/weave-mini/assert-weave-model.ts`) from a clean state, re-pin the hash in
   section (a) once the new artifact is itself gate-clean, and re-attempt the Cameo import.
5. **Update EVIDENCE** with the outcome either way — including a failed attempt. An honest
   "attempted `<date>`, Cameo rejected X, root-caused to Y, fix landed in commit Z" is more
   valuable than silence, and is exactly what this runbook exists to hold over time.

## (g) Honest caveats

- **Cameo-version dependence.** Every step above (menu paths, exact diagnostic wording, which
  constructs a given Cameo build accepts) can vary by Cameo CE version and installed
  plugins/profiles. This runbook describes the stable *shape* of the flow (new project → Textual
  Editor → paste → synchronize → inspect → export), not a byte-exact click sequence guaranteed to
  match any specific installed version. Record the actual version and menu paths used in EVIDENCE
  so this runbook can be tightened for next time.
- **This is a hand-off, not a completed verification.** Nobody in this session had access to a
  running Cameo CE instance (no Java/GUI on this Linux box) — every claim above that "the artifact
  imports cleanly" is a LOCAL claim (Gate 1 + Gate 2, both proven 0-error, both proven able to
  fail via positive controls). The Cameo-side semantic acceptance is unverified until a human runs
  sections (d)–(f) and fills in EVIDENCE below. Do not represent this artifact as "confirmed to
  import into Cameo" until that happens.
