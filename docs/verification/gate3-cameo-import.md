# Gate 3 — Cameo import runbook + evidence record

**Status: NOT YET RUN.** This record documents everything preparable for the first-ever
live Cameo Enterprise Architecture (Cameo CE) import of foundry's own generated output. It is
honest that the import itself has not happened: every screenshot in
`docs/reference/cameo-notation/` is provenance-labeled as coming from the **old** repo
(`sysml-bridge`, 2026-06 sessions) against **hand-authored** probe fixtures — never against a
`.sysml` file this repository's pipeline generated. Foundry's own `examples/angars/out/angars.sysml`
has never been imported into Cameo. The EVIDENCE section at the bottom is empty on purpose; fill
it in only after the human step below actually happens.

This is Gate 3 per README.md: "the manual semantic epilogue: paste the validated `.sysml` into
Cameo Enterprise Architecture's Textual Editor and synchronize. The grammar validator checks
syntax; Cameo is the binding semantic gate." Per `CLAUDE.md` R2/R4, the local grammar validator
(Gate 2) cannot substitute for this step — it checks grammar only, and is specifically documented
as blind to the one semantic defect class this runbook exists to pre-screen: a trace operand
(`satisfy`/`allocate`/`verify`) that resolves to a Definition instead of a Usage. That class parses
clean locally and fails in Cameo with "RequirementDefinition cannot be cast to Feature" (or the
equivalent for Part/Action). Everything below removes every obstacle to the import except the
human step — running it inside a live Cameo CE session — which only Joe can do.

## (b) R4 audit — the specific semantic class the live import must confirm

R4 (`CLAUDE.md`): "`satisfy`/`allocate`/`verify` operands MUST be usages (Features), never
Definitions." The local grammar validator cannot see this — `satisfy <Def> by <Def>;` parses
clean. This is checked here two independent ways, both against the **exact pinned artifact**.

### Text-level audit (the artifact that actually gets pasted into Cameo)

The entire generated file contains exactly **four** occurrences of the `def` keyword, and all four
are `verification def` (the four `VerificationCaseDefinition` blocks — `Verify_Demonstration`,
`Verify_Test`, `Verify_Analysis`, `Verify_Inspection`). That is legitimate and required: a
`VerificationCaseDefinition` owning an `objective { verify <reqUsage>; }` body is exactly the R3
form, and the `VerificationCaseDefinition` itself is never a trace-relationship *operand* — it's
the block-*owner* around the `verify` statements, so it is not subject to R4's "usages only" rule.

```
$ grep -n '\bdef\b' examples/angars/out/angars.sysml
1:verification def Verify_Demonstration {  // @source: Demonstration
16:verification def Verify_Test {  // @source: Test
29:verification def Verify_Analysis {  // @source: Analysis
38:verification def Verify_Inspection {  // @source: Inspection
```

Zero `requirement def`, `part def`, or `action def` declarations exist anywhere in the file.
Every `requirement`, `part`, and `action` declaration uses the bare (usage) keyword:

```
requirement usage declarations (bare "requirement <id> Name;"): 34   (28 system reqs + 6 needs)
part usage declarations        (bare "part Name;"):              7   (1 subsystem + 6 components)
action usage declarations      (bare "action Name;"):            16  (1 wrapper + 15 leaf functions)
```

Since **no Definition-shaped requirement/part/action declaration exists in the file at all**, it
is structurally impossible for any of the trace statements below to resolve to a Definition —
there is nothing Definition-typed for them to reference:

```
satisfy statements:              28   (matches "Created 28 satisfy edges")
allocate statements:             15   (matches "Created 15 model-asserted allocation edges")
dependency (derive) statements:  29   (matches "Created 29 derive edges")
verify statements (in objective  28   (matches "Created 28 verify edges")
  blocks):
```

This is the strongest form of the check available short of the live import: not "I read 30 lines
and they looked fine," but a byte-scan proving the *class* of defect cannot occur in this
specific file, because its only possible source (a Definition declaration) is absent.

### Model-level audit (independent, automated, from `packages/gates`)

`packages/gates/src/relational.ts` implements exactly this rule as `R4-def-operand` (severity:
always `error`). It is exercised — with a genuine positive control — by
`examples/angars/pipeline/seeded-defects.ts` (`pnpm demo:seeded`, part of CI per
`docs/gate-pattern.md` §4). That harness rebuilds the **same** presentation-projected model
(`buildModelStore` → `projectForPresentation`, the identical seam `pnpm demo` serializes from,
not the raw definitional model store) and runs `audit()` from `packages/gates`:

```
$ ANTHROPIC_API_KEY="" pnpm demo:seeded
  (clean control — no defects)   Gate 1 audit()   zero error-severity findings   YES  (0 error findings)
  (a) uncited part …              Gate 1 audit()   GATE03-missing-provenance      YES
  (c) satisfy … source is Definition "SeededDefPart"
                                   Gate 1 audit()   R4-def-operand                 YES  (finding elementId=SeededDefPart severity=error)
  (b) poisoned grammar …          Gate 2 validator …                              YES
Defects caught: 3/3   Clean control: CLEAN
SEEDED-DEFECT HARNESS PASS — every gate caught its planted defect; clean control clean.
```

Two things this proves together, per the "gate never proven to fire" discipline:
1. **The clean control is genuinely clean** — 0 error-severity findings, including 0
   `R4-def-operand` findings, on the actual presentation model this pipeline serializes.
2. **The R4-def-operand rule is proven to fire** — defect (c) plants a real Definition-typed
   trace operand and the rule catches it by rule id *and* element id. A check never shown to fail
   is not a check; this one has been shown to fail, on this exact model shape, in this session.

**Methodology note (a wrong turn worth recording so a future auditor doesn't repeat it):** running
`packages/gates`' `audit()` directly against `FileStore.queryElements()` on
`examples/angars/out/.store` — i.e., the *raw* model store, not the presentation projection —
produces 200 `R4-def-operand` findings. This is **not** a defect in the generated artifact. The
store's canonical element types are `RequirementDefinition` / `PartDefinition` / `ActionDefinition`
by design (reusable-type semantics); `examples/angars/pipeline/cc-presentation.ts` explicitly
re-types them to `RequirementUsage` / `PartUsage` / `ActionUsage` for the presentation/serialization
layer (see its header comment: "The store holds a DEFINITION-based model … "), and that's the model
`serializeToSysml` actually consumes. Auditing the raw store for R4 checks the wrong layer and
produces a false-positive-shaped result. The text-level audit above and the `demo:seeded`
presentation-model audit are the two checks that matter for Gate 3 readiness; both are clean.

**Follow-up filed** (out of scope for this runbook, flagged separately): `pnpm demo`'s own inline
"Step 10: Validation Gate" (in `examples/angars/pipeline/build-model.ts`) hand-reimplements
forward/verify/orphan/provenance/dangling/fidelity checks but does **not** call
`packages/gates`' `audit()`/`relationalFindings()` — so the only code path that actually exercises
the R4 rule against the real ANGARS model is `pnpm demo:seeded`. That script does run in CI, so
R4 has live coverage today; but if `demo:seeded` were ever skipped or its corpus load short-circuited,
`pnpm demo` alone would not catch an R4 regression. Worth wiring `packages/gates` `audit()` into
`build-model.ts`'s own gate directly against the presentation-projected model, rather than relying
on a second script to be the only place the check runs.

## (c) Cameo CE Textual Editor import — step-by-step

Based on how the 2026-06 sessions produced the reference captures in
`docs/reference/cameo-notation/` (see that directory's `README.md` for what each capture shows)
and the renderer-parity workflow in
`docs/superpowers/specs/2026-07-02-sysml-foundry-rebuild-design.md` §"The renderer parity tuning
loop (Phase 4)" ("import each probe into Cameo CE … create the matching view, screenshot"). Adapt
step numbers to whatever Cameo CE version is actually running — the shape of the flow (new project
→ Textual Editor → paste → synchronize → open diagrams → export) is stable across recent versions.

1. **Re-derive and confirm the artifact.** Run `ANTHROPIC_API_KEY="" pnpm demo` from a clean
   working tree; confirm `sha256sum examples/angars/out/angars.sysml` equals
   `fcc269107df9c79c1ac85e0b9c20b5d42ee55f6a183e4f1f62d5fa5c7a1c3ff1`. If it doesn't match, stop —
   re-run the whole validation gate (R2's workflow: edit → regenerate → `pnpm validate:sysml` → 0
   errors) before touching Cameo, and update this record's pinned hash once the new artifact is
   itself gate-clean.
2. **Open Cameo CE.** Create a new project (or open the existing ANGARS working project from the
   2026-06 sessions, if reusing it — note which in the EVIDENCE section below).
3. **Open the Textual Editor / Code Editor perspective** (Cameo's SysML v2 textual-notation panel;
   in recent Cameo CE builds this is Window → Perspective → Textual Editor, or the "SysML v2
   Textual Notation" view depending on version — record the exact menu path actually used in the
   EVIDENCE section, since this is the first time it's being done against foundry output and the
   exact path should be captured for next time).
4. **Paste the pinned `.sysml` content** — the full contents of `examples/angars/out/angars.sysml`
   (confirmed hash from step 1) — into a new textual-notation resource/package in the project.
5. **Synchronize / Commit the textual notation to the model.** This is the step that runs Cameo's
   own SysML v2 parser and semantic resolver over the pasted text — the step Gate 2's local
   validator cannot substitute for, because it resolves cross-references semantically (Definition
   vs. Usage, feature typing), not just grammatically.
6. **Record every diagnostic Cameo reports** — even ones that don't block the sync — in the
   EVIDENCE section. A clean sync with zero diagnostics is the target; anything Cameo flags is
   itself evidence, whether or not it turns out to matter.
7. **Create the five views** matching the gallery in `README.md` / the reference captures in
   `docs/reference/cameo-notation/` (BDD/General, IBD/Interconnection, Activity, Requirements,
   Traceability) so the import can be checked feature-by-feature against what the local viewer
   rendered to `examples/angars/out/renders/*.pdf` in this session.
8. **Screenshot each view** (or export to PDF/PNG the way the 2026-06 sessions did — see
   `docs/reference/cameo-notation/README.md`'s Provenance table: native PNG export for some views,
   `pdftoppm -png -r 150` rasterization of exported PDFs for others) and save under
   `docs/reference/cameo-notation/` with a provenance label that says **foundry / 2026-07 / this
   run** — explicitly distinct from the existing 2026-06 `sysml-bridge` captures, so the gallery
   never conflates "old repo, hand-authored probes" evidence with "this repo's own generator,
   proven live" evidence.

## (e) On failure

Per R2: a non-zero/non-clean result at any step above **stops** the claim that this file imports.
Do not guess a fix.

1. **Grammar-shaped Cameo diagnostic** (Cameo rejects a construct the local validator accepted —
   should not happen if Gate 2 passed, but if it does, the vendored grammar and Cameo's parser have
   diverged): read `docs/sysml-v2-reference/` (the vendored `.g4` grammar and `cheatsheet.md`) for
   the correct form. Never guess syntax from memory (R1). File the divergence as its own note in
   this document once understood, since it means the vendored grammar needs an update.
2. **Semantic diagnostic — R4 def-operand or similar** ("X cannot be cast to Feature" or
   equivalent): this means section (b)'s audit above missed something, or a *later* regeneration
   of `angars.sysml` (with a different SHA-256 than the one pinned here) introduced a regression.
   Fix in `packages/sysml/src/sysml-serializer.ts` / `examples/angars/pipeline/cc-presentation.ts`
   (the def→usage projection), never by hand-patching the `.sysml` text. Re-run the full gate
   (R2's workflow) from step 2, re-pin the hash in section (a), and re-attempt the import.
3. **Element count mismatch** (Cameo shows fewer elements than `audit.json`): check whether the
   paste was truncated, or whether Cameo silently rejected part of the resource. Re-paste from a
   freshly-copied `examples/angars/out/angars.sysml`, not a modified/partial buffer.
4. **Anything else Cameo reports**: record it verbatim in EVIDENCE below even if it doesn't block
   the sync — an unexplained warning today is a lead for the next regression. Do not close this
   record as "PASS" while any diagnostic is unexplained.

Whatever the outcome, update EVIDENCE below with what actually happened — including a failed
attempt. An honest "attempted 2026-07-14, Cameo rejected X, root-caused to Y, fix pending" is more
valuable than silence, and is exactly what this record exists to hold.
